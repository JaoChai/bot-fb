# สรุปออเดอร์เองเมื่อลูกค้าโอนข้ามขั้นตอน (Order Reconstruction)

วันที่: 2026-07-31
สถานะ: design (รออนุมัติก่อนเขียนแผน implementation)

## ปัญหา

ลูกค้าขาประจำที่จำเลขบัญชีร้านได้ โอนเงินทันทีโดยไม่รอบอทส่งข้อความสรุปยอด ระบบตรวจสลิปผ่าน
(เงินเข้าจริง บัญชีถูก ไม่ซ้ำ) แต่หาไม่เจอว่าลูกค้าสั่งอะไร จึงบันทึกเป็น `no_pending_order`
ตอบลูกค้าด้วยข้อความกลางๆ ("ขอตรวจสอบยอดสักครู่") และเด้ง Telegram ให้เจ้าของไปเปิดแชทไล่อ่านเอง

### ข้อมูลจริงจาก prod (ตรวจ 2026-07-31)

- `slip_verifications` ทั้งหมด 125 แถว: `passed` 93 · `manual_confirmed` 13 · **`no_pending_order` 5 (4%, รวม 6,600 บาท)**
- เคสล่าสุดเกิดวันนี้ 2026-07-31 16:02 น. (แชท #92 ยอด 1,100) — เจ้าของต้องกดยืนยันเองภายใน 24 วินาที
- แชท #92 เจอ 3 ครั้ง (14, 18, 31 ก.ค.) = ลูกค้าประจำรายเดียวกัน โอนข้ามขั้นเป็นนิสัย

### สาเหตุที่แท้จริง (ไล่แชทจริงทั้ง 4 เคสที่ข้อมูลยังอยู่)

ข้อมูลออเดอร์ **มีอยู่ในแชทแล้วเกือบทุกเคส** แต่ตัว parser ที่เป็น regex มองไม่เห็น:

| เคส | ข้อความบอทก่อนลูกค้าโอน | ทำไมหลุด |
|---|---|---|
| #92 31 ก.ค. (1,100) | "เพิ่ม Nolimit Level Up+ Personal (ผูกบัตร) 1 ตัว **ราคา** 1,100 บาท... พิมพ์ยืนยัน" | `isConfirmMessage()` บังคับต้องมีคำว่า "รวม" (`PaymentMessageDetector.php:206`) ข้อความนี้ใช้ "ราคา" |
| #92 18 ก.ค. (2,200) | "...2 ตัว รวม 2,200 บาท พิมพ์ยืนยัน" | ตอนนั้น fallback ยังไม่ deploy (ขึ้น 28 ก.ค. commit `0271914`) |
| #1072 18 ก.ค. (1,100) | "เพิ่ม...1 ตัวลงตะกร้าแล้ว รวม: 1,100 บาท" | จับยอดได้ แต่ดึงรายการไม่ได้ (บรรทัดชื่อสินค้าไม่มี "บาท") → `requireItems` คืน null |
| #169 17 ก.ค. (1,100) | ไม่มีเลย — บอทตอบ error แล้วลูกค้าโอนทันที | ในแชทมีแค่คำลูกค้า "ซื้อเฟส personal 1 ผูกบัตร" |

ปัญหาไม่ใช่ "ลูกค้าไม่ทำตามขั้นตอน" (ห้ามไม่ได้ และจะเกิดต่อไปเรื่อยๆ) แต่คือ
**ระบบใช้ regex ไล่จับข้อความที่ LLM เขียนไม่ซ้ำเดิม** — patch ไปรอบหนึ่งเมื่อ 28 ก.ค. แล้ววันนี้ยังหลุดอีก

### ของแถมที่เจอระหว่างตรวจ

ตาราง `orders` มีหลายใบที่ยอด 2,200 แต่บันทึก `Nolimit Personal x1` (order #1622, #1634, #1657)
= จำนวนเพี้ยนโดยไม่มีใครรู้ ตัวเช็ค "ราคา × จำนวน = ยอดโอน" ในดีไซน์นี้จับเคสแบบนั้นได้ด้วย

## ทางเลือกที่พิจารณา

- **A. ให้ LLM สร้างออเดอร์จากบทสนทนา + ใช้ยอดเงินเป็นตัวตรวจ** ← เลือก
- **B. ขยาย regex อย่างเดียว** — ถูกและเร็ว แต่เป็นเกมวิ่งไล่ที่ไม่จบ และช่วยเคส #169 ไม่ได้ (นำมาใช้เป็นส่วนเสริมแทน)
- **C. แก้ prompt ให้บอทส่งเลขบัญชีเร็วขึ้น** — ไม่แก้ต้นเหตุ ลูกค้าประจำมีเลขบัญชีในมืออยู่แล้ว (ทำทีหลังได้ ไม่อยู่ใน scope นี้)

## ดีไซน์

### 1. ลำดับด่าน

จุดเดียวที่แก้คือเช็คข้อ 3 ใน `SlipVerificationService::verify()` (`:292`) ซึ่งวางด่านเรียงกันอยู่แล้ว

```
สลิปผ่านธนาคาร (เงินเข้าจริง · บัญชีร้าน · ไม่ซ้ำ)
  ด่าน 1  findExpectedPayment()            regex ข้อความสรุปยอด+เลขบัญชี   → เจอ = จบ (ฟรี)
  ด่าน 2  findExpectedFromConfirmMessage() regex ข้อความยืนยันขั้น 2       → เจอ = จบ (ฟรี)
  ด่าน 3  OrderReconstructor  ← ใหม่       LLM อ่านบทสนทนา                 → เรียกเฉพาะตอน 1+2 พลาด (~4% ของสลิป)
```

### 2. `OrderReconstructor` (ไฟล์ใหม่)

โครงเดียวกับ `LLMOrderItemExtractor` ที่มีอยู่ (utility model ต่อบอท, temperature ต่ำ, ไม่ throw,
ทุก error path คืนค่าว่าง) แต่ขอบเขตต่างกัน: อ่าน **ทั้งบทสนทนา** ไม่ใช่ข้อความเดียว

อินพุต:
- บทสนทนา 15 ข้อความล่าสุด **ทั้งฝั่งลูกค้าและบอท** (ของเดิมอ่านแต่ข้อความบอท — เคส #169 ข้อมูลอยู่ฝั่งลูกค้า)
- รายการสินค้า + ราคาจาก `product_stocks` (4 แถว)
- ยอดที่โอนมาจริงจากสลิป

เอาต์พุต JSON: `{items:[{slug, qty}], confidence, quote}` โดย `quote` = ข้อความในแชทที่ใช้เป็นหลักฐาน

### 3. ด่านตรวจก่อนเชื่อ LLM (โค้ดธรรมดา ไม่ใช่ AI)

1. ทุก `slug` ต้องมีจริงใน `product_stocks` และ `in_stock = true`
2. **Σ(price × qty) = ยอดในสลิป** (± `slip_amount_tolerance` เดิมของบอท)
3. ชื่อสินค้าหรือ alias ต้องปรากฏในบทสนทนาจริง — กัน LLM แต่งของที่ไม่มีใครพูดถึง

### 4. ผลลัพธ์ 3 ชั้น

| ชั้น | เงื่อนไข | ระบบทำอะไร |
|---|---|---|
| มั่นใจ | ผ่านครบ 3 ข้อ + ประกอบยอดได้แบบเดียว | `passed` → เดินเส้นทางเดิมทั้งหมด (ตอบลูกค้า → สร้างออเดอร์ → `ReserveAccountStock` ส่งของ) + Telegram **เงียบ ไม่มีปุ่ม** แจ้งว่าระบบสรุปเอง |
| กำกวม | ยอดตรงแต่ประกอบได้หลายแบบ (1,100 = Personal หรือ BM ราคาเท่ากัน) หรือ confidence ต่ำ | ยังไม่ส่งของ → การ์ด Telegram พร้อมปุ่มตัวเลือกที่ประกอบยอดได้ เจ้าของกดปุ่มเดียวจบ |
| ไม่รู้ | ประกอบยอดไม่ได้เลย | พฤติกรรมเดิม (`no_pending_order`) แต่การ์ดแนบ 3 ข้อความล่าสุดในแชทมาให้ ไม่ต้องเปิดแอปไล่อ่าน |

**ตัดสินแล้วว่าไม่ทำในรอบนี้:** ให้บอทถามลูกค้ายืนยันเอง ("รับ Personal 1 ตัวใช่ไหมครับ?")
เพราะต้องเพิ่มสถานะค้าง จับคำตอบลูกค้า และ timeout กันเงินค้าง — งานใหญ่กว่าอีกสองชั้นรวมกัน
รอวัดจากข้อมูลจริงก่อนว่าเหลือเคสกำกวมกี่เคสต่อเดือน แล้วค่อยตัดสินใจ

### 5. ของที่ต้องเพิ่ม/แก้

- migration: `product_stocks.price` (decimal nullable) + กรอกค่า 4 แถว + เพิ่มช่องราคาในหน้าจัดการสต็อกที่มีอยู่
- migration: `slip_verifications.order_source` (`summary` / `confirm` / `llm` / `manual` / null) — ไว้วัดว่าด่านไหนช่วยจริง
- ไฟล์ใหม่: `app/Services/Payment/OrderReconstructor.php` (~120 บรรทัด)
- patch เล็กที่ `PaymentMessageDetector::isConfirmMessage()` + `parseConfirmData()`: รับ "ราคา" เพิ่มจาก "รวม"
- patch เล็กที่ `SlipVerificationService::findExpectedFromConfirmMessage()` (`:179-182`): ตอนนี้เจอข้อความ
  ที่ยอดตรงแต่ดึงรายการไม่ได้ แล้ว `return null` ทิ้งทั้งลูป → ต้องวนดูข้อความถัดไปต่อ
- การ์ด Telegram: เพิ่มรูปแบบ "เงียบ" (ไม่มีปุ่ม) และแบบ "ไม่รู้" ที่แนบข้อความล่าสุด
- **ไม่แตะ:** เส้นทางสลิปที่ผ่านปกติ 93 ใบ — ทุกอย่างเพิ่มหลังด่าน 2 พลาดเท่านั้น

### 6. ราคาสินค้า

เจ้าของยืนยันว่าราคาคงที่ ไม่ค่อยเปลี่ยน ราคาที่ยืนยันจากข้อมูลจริงแล้ว:

| สินค้า | ราคา/ชิ้น | ที่มา |
|---|---|---|
| Nolimit Level Up+ Personal | 1,100 | prompt flow 24 + แชทจริง |
| Nolimit Level Up+ BM | 1,100 | prompt flow 24 (ราคาเท่ากับ Personal → เป็นที่มาของชั้น "กำกวม") |
| Page | 199 | prompt flow 24 (upsell) |
| G3D | 50 | derive จาก `order_items` 40+ ออเดอร์ (2 ตัว=100 · 5=250 · 10=500 · 20=1,000 ตรงกันทุกใบ) |

ให้เจ้าของ confirm ตัวเลขนี้อีกครั้งตอนกรอกลง `product_stocks` (1 นาที) — ราคาผิด = ตัวตรวจผิด
ส่วนลดเป็นเคสพิเศษจริงๆ ซึ่งจะตกไปชั้น "กำกวม"/"ไม่รู้" เอง เพราะยอดไม่ตรง — ถือว่าถูกต้องตามเจตนา

### 7. ค่าใช้จ่าย

เรียก LLM เพิ่มเฉพาะเคสที่สองด่านแรกพลาด = ~5 ครั้งต่อ 3 สัปดาห์ ใช้ utility model ที่ตั้งไว้แล้วต่อบอท
ถ้าไม่ได้ตั้ง utility model หรือเรียกพลาด → คืนค่าว่าง ตกไปชั้น "ไม่รู้" = พฤติกรรมเดิม ไม่มีอะไรแย่ลง

## วิธีพิสูจน์ว่าใช้ได้จริง

ทำบทสนทนาจริงทั้ง 5 เคสจาก prod เป็น fixture แล้ววัดกับออเดอร์ที่เจ้าของยืนยันจริงในตาราง `orders`:

- #92 (31 ก.ค.) → มั่นใจ, Personal ×1 = 1,100
- #92 (18 ก.ค.) → มั่นใจ, Personal ×2 = 2,200
- #1072 (18 ก.ค.) → มั่นใจ, Personal ×1 = 1,100
- #169 (17 ก.ค. บอทพัง ไม่มียอดในแชท) → ต้องได้ "กำกวม" หรือ "ไม่รู้" เท่านั้น **ห้ามส่งของเอง**
- เทสต์ดักถอยหลัง: LLM ตอบของที่ยอดรวมไม่ตรง → ต้องถูกปัดตกทุกครั้ง
- เทสต์ว่าด่าน 1/ด่าน 2 ที่ทำงานได้อยู่แล้ว ไม่เรียก LLM เลย (คุมค่าใช้จ่าย)

เกณฑ์ผ่าน: 4 ใน 5 เคสระบบจัดการเองได้ และไม่มีเคสไหนส่งของผิด

## ความเสี่ยงที่ยอมรับ

- LLM เดาถูกยอดแต่ผิดรุ่น (Personal vs BM ราคาเท่ากัน) → กันด้วยกติกา "ประกอบได้หลายแบบ = กำกวม เสมอ"
  แม้ LLM จะมั่นใจก็ตาม
- ราคาใน `product_stocks` ไม่ตรงกับราคาที่ขายจริง → checksum จะไม่ผ่าน ตกไปชั้น "ไม่รู้"
  = พฤติกรรมเดิม ไม่มีการส่งของผิด
