# Prompt Eval — เทสต์กันบอทพังซ้ำ

เครื่องมือรันเทสต์ system prompt ของบอทกับเคสจริงที่เคย "พัง" มาก่อน เพื่อเช็คว่าแก้ prompt
หรือแก้ knowledge base (KB) รอบนี้แล้ว **บอทไม่กลับไปตอบผิดซ้ำเหตุการณ์เดิม**

## ต้องรันเมื่อไหร่

**รันก่อนและหลังแก้ `flows.system_prompt` (หรือ KB) ของบอททุกครั้ง** ไม่ว่าจะแก้เองหรือให้ Claude
แก้ให้ — รันก่อนเพื่อดูสถานะตั้งต้น รันหลังเพื่อยืนยันว่าไม่มีเคสเดิมตกเพิ่ม ก่อนเอา prompt ขึ้น prod จริง

## มันทำอะไร

คำสั่งจะยิงข้อความลูกค้าจำลอง (ตามแต่ละเคส) เข้าไปหาบอทจริงผ่าน AI จริง แล้วเอาคำตอบที่ได้มา
เทียบกับเงื่อนไขที่ตั้งไว้ต่อเคส เช่น "คำตอบต้องมีคำว่า X" หรือ "ห้ามมีคำว่า Y" — **ไม่มีการเขียน
อะไรลงฐานข้อมูลเลย** (ไม่สร้าง conversation ไม่บันทึกข้อความ) **และปิดแคชคำตอบ (semantic cache)
ระหว่างรันด้วย** จึงไม่มีทางที่คำตอบจากการรันเทสต์จะไปโผล่ตอบลูกค้าจริง หรือคำตอบเก่าจากการรันเทสต์
ครั้งก่อนจะมาปนกับผลรันครั้งนี้ ปลอดภัยรันได้เรื่อย ๆ

ชุดเคสตอนนี้มี 20 เคส และทุกเคสมาจากเหตุการณ์จริงที่เคยเกิดบน prod (มีคอมเมนต์กำกับที่มาไว้เหนือ
แต่ละเคสในไฟล์ `config/prompt-eval-cases.php` เช่น หมายเลขบทสนทนา/วันที่/PR)

## วิธีรัน (เครื่อง dev)

รันจากโฟลเดอร์ `backend/` (ที่มีไฟล์ `artisan`):

```bash
# รันทั้ง 20 เคส รอบเดียว
php artisan prompt:eval

# รันซ้ำ 3 รอบต่อเคส (แนะนำก่อนขึ้น prod จริง — ดูหัวข้อ "ทำไมต้องรันหลายรอบ")
php artisan prompt:eval --runs=3

# รันเฉพาะบางเคส (คั่นด้วย comma ได้) — id ของแต่ละเคสอยู่ในไฟล์ config
php artisan prompt:eval --filter=pixel_premade

# เก็บผลเป็นไฟล์ JSON ไว้ดูย้อนหลัง/ส่งต่อ
php artisan prompt:eval --json=/tmp/eval.json
```

จะได้ผลแบบนี้ต่อเคส:

```
✅ [pixel_premade] ขอบัญชีที่สร้างพิกเซลมาแล้ว (conv #1539, 21 ส.ค.) (3/3 รอบผ่าน)
❌ [bm_with_unit] BM+หน่วยนับ = สั่งซื้อ ห้ามถามซ้ำ (regression คู่กับ 6) (2/3 รอบผ่าน)
   - ต้องมี "5,500" แต่ไม่พบ
   คำตอบ: BM มีกี่ตัวก็ได้ครับ...
```

แล้วปิดท้ายด้วยสรุปรวม (ผ่านกี่/ทั้งหมดกี่เคส, เวลารวม, ค่าใช้จ่ายรวมโดยประมาณ)

**เคสไหนถือว่า "ผ่าน" ต้องผ่านครบทุกรอบที่สั่งด้วย `--runs`** — ถ้ารัน `--runs=3` แล้วผ่าน 2/3 ถือว่า
เคสนั้นตก

## วิธีรันบน prod

```bash
railway ssh -- php /var/www/html/artisan prompt:eval
```

**หมายเหตุ:** container บน prod รากอยู่ที่ `/var/www/html` ไม่ใช่ `/app` — ต้องระบุ path เต็มแบบนี้

## ทำไมต้องรันหลายรอบ (`--runs`)

บอทตอนนี้ตั้ง temperature ไว้ที่ 0.40 คำตอบจึงไม่ได้เหมือนเดิม 100% ทุกครั้งที่ถามคำถามเดียวกัน —
รันรอบเดียวอาจ "บังเอิญผ่าน" หรือ "บังเอิญตก" ก็ได้ ก่อนขึ้น prod จริงแนะนำสั่ง `--runs=3` ขึ้นไป
เพื่อลดโอกาสหลอกตัวเอง

## วิธีเพิ่มเคสใหม่

**กฎ: ทุกครั้งที่แก้ prompt เพราะมีเคสจริงบน prod มาพัง ต้องเพิ่มเคสนั้นเข้าไฟล์ชุดทดสอบด้วยเสมอ**
ไม่งั้นครั้งหน้าที่แก้ prompt เรื่องอื่น อาจทำเคสเดิมพังซ้ำแบบไม่มีใครรู้

1. เปิด `config/prompt-eval-cases.php`
2. เพิ่ม element ใหม่ในอาร์เรย์ พร้อมคอมเมนต์บอกที่มา (เลขบทสนทนา/วันที่/PR) ไว้เหนือเคส
3. รันเฉพาะเคสนั้นยืนยันก่อน commit: `php artisan prompt:eval --filter=<id ที่ตั้งไว้>`

ตัวอย่างเคส (สมมติ — ไม่ใช่เหตุการณ์จริง ใช้เพื่อสาธิตรูปแบบเท่านั้น):

```php
// [ตัวอย่าง] ลูกค้าถามราคาแบบสั้น ๆ ห้ามโดน guardrail กันคำถามที่ไม่เกี่ยวสินค้าบล็อก
[
    'id' => 'price_short_question',
    'label' => '[ตัวอย่าง] ลูกค้าถามราคาแบบสั้น ๆ ห้ามโดน guardrail บล็อก',
    'message' => 'ราคา?',
    'expect_off_topic' => false,
    'must_contain' => [
        ['1,100'],
    ],
    'must_not_contain' => ['ไม่เข้าใจคำถาม'],
],
```

เคสจริงที่เพิ่มเข้าไฟล์ต้องใส่เลขบทสนทนา/วันที่/PR ที่มาจริงเสมอ (ดูตัวอย่างเคสจริงในไฟล์
`config/prompt-eval-cases.php` เช่น `pixel_premade`) — ห้ามใส่เลขอ้างอิงที่แต่งขึ้นเองแบบเคสตัวอย่าง
ด้านบน

field ที่ใช้ได้ในแต่ละเคส (ทุก field เป็น optional ยกเว้น `id`/`label`/`message`):

| field | ใช้ทำอะไร |
|---|---|
| `id` | ตัวระบุไม่ซ้ำกัน ใช้กับ `--filter` |
| `label` | คำอธิบายเคสภาษาไทย |
| `history` | บทสนทนาก่อนหน้า (มี = จำลองว่าลูกค้าคุยมาแล้วหลายรอบ, ไม่มี = เริ่มทักครั้งแรก) |
| `message` | ข้อความล่าสุดจากลูกค้าที่จะยิงเข้าไป |
| `must_contain` | คำตอบต้องมีคำเหล่านี้ (ดูกติกา OR/AND ด้านล่าง) |
| `must_not_contain` | คำตอบห้ามมีคำเหล่านี้เลยแม้แต่คำเดียว |
| `expect_off_topic` | ต้อง (true) หรือห้าม (false) โดน guardrail กันคำถามนอกเรื่องบล็อก |
| `expect_order` | ยอด/รายละเอียดออเดอร์ที่ต้องตรง เมื่อคำตอบต้องมีการสรุปออเดอร์ |

กติกาของ `must_contain`: แต่ละแถวย่อย (`[...]`) คือกลุ่ม "หรือ" — เจอคำใดคำหนึ่งในกลุ่มก็ถือว่ากลุ่ม
นั้นผ่าน แต่ **ทุกกลุ่มต้องผ่านหมด** คำตอบถึงจะผ่านเคส เช่นตัวอย่างเคส `pixel_premade` ต้องมีทั้งคำว่า
"ไม่มี" และคำในกลุ่ม "สร้างพิกเซลเองได้/สร้างเองได้/สร้างพิกเซลเอง" (มีคำใดคำหนึ่งในกลุ่มก็พอ)

**หลักการเขียน `must_not_contain` — ใช้ "วลีคำสัญญาเชิงบวก" (ลงท้าย ...ได้/...ให้) แทนคำนามเปล่า**
ภาษาไทยปฏิเสธด้วยการเติม "ไม่"/"ไม่สามารถ" ไว้ **หน้า** วลี ไม่ใช่แปลงคำ — คำตอบที่ถูกต้อง (ปฏิเสธ)
มักมีวลีต้องห้ามซ้อนอยู่ข้างในพอดี เช่นเคส `staggered_pickup` ถ้าเขียน `must_not_contain: ['ฝากไว้']`
คำตอบที่ถูกต้อง "ไม่สามารถฝากไว้ให้ได้ครับ" จะโดนตัดสินว่าผิดทันที (มีคำว่า "ฝากไว้" ซ้อนอยู่จริง)
แก้โดยเขียนเป็นวลีเต็มที่ลงท้ายด้วยคำสัญญาเชิงบวก เช่น `'ฝากไว้ให้ได้'` แทน — "ไม่สามารถฝากไว้ให้ได้"
ไม่มีสตริง "ฝากไว้ให้ได้" ซ้อนอยู่ข้างในเลย จึงไม่ต้องพึ่ง negative lookbehind อีก (ยังใช้ lookbehind
ได้ในเคสที่ตัวคำเองก็เป็นคำที่ต้องห้ามจริง ๆ ไม่มีคำสัญญาบวกให้ตัด เช่น `page_no_bm_push`) —
ดูตัวอย่างเปรียบเทียบทั้ง 2 แบบได้ในไฟล์ `config/prompt-eval-cases.php` เคส `staggered_pickup` (วลี
คำสัญญาบวก) กับ `page_no_bm_push`/`vat_no_promise` (negative lookbehind)

## ข้อจำกัดที่ต้องรู้

- **มีค่าใช้จ่ายเล็กน้อยทุกครั้งที่รัน** เพราะแต่ละเคสยิงไปหา AI จริง 1 ครั้ง (ยิ่งตั้ง `--runs` สูง
  ยิ่งยิงหลายครั้ง) และแต่ละเคสใช้เวลาประมาณ 5-10 วินาที รันทั้งชุด 20 เคสจึงไม่ใช่ของฟรีหรือของเร็ว
  ไม่ควรรันพร่ำเพรื่อโดยไม่มีเหตุผล
- **ชุดนี้กันได้แค่ "เคสเก่าพังซ้ำ"** ไม่ได้การันตีว่าบอทจะตอบถูกในสถานการณ์ใหม่ที่ยังไม่เคยเจอ —
  เจอเคสแปลกใหม่พังบน prod เมื่อไหร่ ให้ทำตามหัวข้อ "วิธีเพิ่มเคสใหม่" ด้านบนเพื่อปิดช่องโหว่ถาวร
- ถ้าเคสตกตั้งแต่รอบแรกหลังเพิ่มเคสใหม่ ให้พิจารณาก่อนว่าเกณฑ์ที่ตั้งไว้เข้มเกินไปหรือเปล่า (เช่น
  บังคับคำเป๊ะเกินไป) แล้วปรับที่ **เกณฑ์ในเคส** — อย่าไปแก้ prompt ตามเกณฑ์ที่ตั้งผิด
- **เคสตกอาจไม่ได้แปลว่า prompt พังเสมอ — บอทมีการฉีดข้อมูลสต็อกจริงเข้า prompt ทุกครั้ง**
  (`RAGService.php` ราวบรรทัด 400-409) เคสที่อ้างอิงจำนวน/การมีสินค้า เช่น `bm_with_unit` (ต้องมี BM
  เหลือ ≥5) หรือ `qty_bulleted_20` (ต้องมี G3D เหลือ ≥20) จะตกได้ถ้าของหมดหรือเหลือน้อยกว่าที่เคสสมมติ
  ไว้จริง ๆ บน prod — **ต้องเช็คสต็อกจริงก่อนสรุปว่า prompt พัง และห้ามลดทอนเกณฑ์ในเคสเพราะเหตุนี้**
  (ถ้าลดเกณฑ์ เคสจะไม่มีทางจับ regression จริงได้อีกต่อไป)
- **เคส `order_payload_total` เป็นเคสเดียวที่ทราบว่า flaky ~8%/รอบ** — LLM ปล่อยบล็อก
  `[[ORDER]]...[[/ORDER]]` ไม่ปิดเป็นบางครั้งเพราะชนเพดาน token (สุ่ม ไม่เกี่ยวกับ prompt ผิด และ
  production มี `OrderPayloadExtractor` รับมืออาการนี้อยู่แล้ว) ถ้าเคสนี้ตกเดี่ยว ๆ (เคสอื่นผ่านหมด)
  ให้รัน `php artisan prompt:eval --filter=order_payload_total` ซ้ำอีก 2-3 รอบก่อนสรุปว่าเป็น
  regression จริง — failure message จะบอกแยกให้ว่าเป็น "ไม่มีบล็อกเลย" (น่าสงสัยว่า regression จริง)
  หรือ "บล็อกไม่ปิด" (อาการสุ่มที่รู้จักแล้ว)

## ภาคผนวกทางเทคนิค (สำหรับ dev)

- คำสั่งอยู่ที่ `app/Console/Commands/PromptEval.php` (signature: `prompt:eval {--bot=26}
  {--runs=1} {--filter=} {--json=}`), ตัวรันจริงอยู่ที่
  `app/Services/PromptEval/PromptEvalRunner.php`
- ทดสอบผ่าน `tests/Unit/PromptEvalRunnerTest.php` (assertion engine) และ
  `tests/Feature/Console/PromptEvalCommandTest.php` (command wiring)
- เคสที่ไม่มี `history` เดินทางผ่าน `AIService::generateResponse()`, เคสที่มี `history` เดินทางผ่าน
  `RAGService::generateResponse()` (ใช้ flow เริ่มต้นของบอทที่ระบุด้วย `--bot`) — ทั้งสองเรียกด้วย
  `conversation: null` เสมอ จึงไม่มีการบันทึก conversation/messages ลง DB
- **เคสที่มี `history` เดินทาง RAGService ตรงๆ ข้าม post-processing บางชั้นที่ปกติ
  `AIService::generateResponse()` ทำให้เสมอ** เช่น `StockGuardService` (บล็อกการขายของหมดสต็อกแบบ
  hard-block) และ `GuardrailOutputSanitizer` (ตาข่ายสุดท้ายกัน code block/markdown/AI-admission
  หลุด) — `PromptEvalRunner` ชดเชยให้เฉพาะการตัด marker `[[OFFTOPIC]]` และบล็อก
  `[[ORDER]]...[[/ORDER]]` เท่านั้น (ดูหัวข้อ needle ด้านล่าง) ดังนั้นข้อความที่เคสที่มี `history`
  เอาไปเทียบอาจต่างจากที่ลูกค้าเห็นจริงเล็กน้อยในบางกรณี (เช่น เคสของหมดสต็อกที่ปกติ StockGuard
  จะบล็อกให้)
- `PromptEvalRunner::run()` ปิด `SemanticCacheService->enabled` ของ instance จริงที่ `RAGService`
  ถืออยู่ผ่าน `ReflectionProperty` ก่อนเรียก LLM แล้วคืนค่าเดิมด้วย `finally` เสมอ — กันไม่ให้เขียน
  ทับ `rag_cache` (semantic cache ที่เสิร์ฟลูกค้าจริง, similarity 0.92, TTL 60 นาที) และกันไม่ให้
  เคสได้ cache hit จากผลรันครั้งก่อนแทนที่จะยิง LLM ใหม่จริง **กลไกนี้ทำงานได้เพราะ
  `PromptEvalRunner` ถูก resolve ผ่าน service container เท่านั้น** (method injection ใน
  `PromptEval::handle()`) จึงได้ `RAGService`/`SemanticCacheService` singleton ตัวเดียวกับที่
  `AIService` ใช้จริง — ถ้าใครแก้โค้ดให้สร้าง `new PromptEvalRunner(...)` เองแทน การปิดแคชนี้จะ
  ไม่มีผลใด ๆ (ได้ instance คนละตัว)
- needle ใน `must_contain`/`must_not_contain` ที่ **ขึ้นต้นด้วย `/`** จะถูกตีความเป็น regex เสมอ
  (รองรับ modifier ท้าย เช่น `/1,?100/u`, `/(?<!ไม่)ได้/`) นอกนั้นเทียบแบบ substring แบบไม่สนตัวพิมพ์
  เล็ก-ใหญ่ — pattern ที่ compile ไม่ผ่านจะทำให้เคสตกพร้อม failure บอกชัดว่า pattern ไหนพัง ไม่ตีกลับ
  ไปเทียบแบบ substring เงียบ ๆ (เคยเป็นแบบนั้นมาก่อน ทำให้เคสที่ตั้งใจเขียน regex แต่พิมพ์ modifier
  ผิดหลอกตัวเองว่าผ่าน/ตกโดยไม่มีใครรู้)
  ก่อนเทียบ runner จะ normalize คำตอบ: ตัดตัวคั่นข้อความ (bubble separator) `|||` ออก แล้วยุบ
  whitespace ต่อเนื่องให้เหลือช่องว่างเดียว — ถ้าคำตอบว่างเปล่าหลัง normalize (เช่น LLM หมด token
  กลางทาง) เคสตกเสมอ แม้เคสนั้นจะมีแค่ `must_not_contain` (ซึ่งปกติจะผ่านฟรีถ้าไม่มีอะไรให้เจอ)
- `expect_order` เทียบกับ `order_payload` ที่ตัดออกมาจากบล็อก `[[ORDER]]...[[/ORDER]]` ใน
  คำตอบดิบ (ใช้ `!=` แบบ loose comparison ต่อ key) — เส้นทาง RAGService (มี `history`) ที่ดึงบล็อก
  เองไม่เจอ จะแยก failure message เป็น 2 แบบ: **ไม่มีบล็อก `[[ORDER]]` เลย** (น่าสงสัยว่า regression
  จริง) กับ **บล็อกไม่ปิด** (`[[/ORDER]]` หาย — อาการสุ่ม ~8% ที่ production รับมือแล้วด้วย
  `OrderPayloadExtractor::STRIP_PATTERN`, `PromptEvalRunner` ใช้ pattern เดียวกันตัดบล็อกออกจาก
  response ที่เอาไปเทียบ must_contain/must_not_contain ด้วย ไม่ว่าจะปิดครบหรือไม่)
- exit code: `0` เมื่อทุกเคสผ่านครบตาม `--runs`, `1` เมื่อมีอย่างน้อย 1 เคสตก — ใช้เช็คใน script/CI ได้
