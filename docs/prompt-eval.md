# Prompt Eval — เทสต์กันบอทพังซ้ำ

เครื่องมือรันเทสต์ system prompt ของบอทกับเคสจริงที่เคย "พัง" มาก่อน เพื่อเช็คว่าแก้ prompt
หรือแก้ knowledge base (KB) รอบนี้แล้ว **บอทไม่กลับไปตอบผิดซ้ำเหตุการณ์เดิม**

## ต้องรันเมื่อไหร่

**รันก่อนและหลังแก้ `flows.system_prompt` (หรือ KB) ของบอททุกครั้ง** ไม่ว่าจะแก้เองหรือให้ Claude
แก้ให้ — รันก่อนเพื่อดูสถานะตั้งต้น รันหลังเพื่อยืนยันว่าไม่มีเคสเดิมตกเพิ่ม ก่อนเอา prompt ขึ้น prod จริง

## มันทำอะไร

คำสั่งจะยิงข้อความลูกค้าจำลอง (ตามแต่ละเคส) เข้าไปหาบอทจริงผ่าน AI จริง แล้วเอาคำตอบที่ได้มา
เทียบกับเงื่อนไขที่ตั้งไว้ต่อเคส เช่น "คำตอบต้องมีคำว่า X" หรือ "ห้ามมีคำว่า Y" — **ไม่มีการเขียน
อะไรลงฐานข้อมูลเลย** (ไม่สร้าง conversation ไม่บันทึกข้อความ) ปลอดภัยรันได้เรื่อย ๆ

ชุดเคสตอนนี้มี 20 เคส และทุกเคสมาจากเหตุการณ์จริงที่เคยเกิดบน prod (มีคอมเมนต์กำกับที่มาไว้เหนือ
แต่ละเคสในไฟล์ `config/prompt-eval-cases.php` เช่น หมายเลขบทสนทนา/วันที่/PR)

## วิธีรัน (เครื่อง dev)

รันจากโฟลเดอร์ `backend/` (ที่มีไฟล์ `artisan`):

```bash
# รันทั้ง 20 เคส รอบเดียว
php artisan prompt:eval

# รันซ้ำ 3 รอบต่อเคส (แนะนำก่อนขึ้น prod จริง — ดูหัวข้อ "ทำไมต้องรันหลายรอบ")
php artisan prompt:eval --runs=3

# รันเฉพาะบางเคส (คั่นด้วย comma ได้) — id ของแต่ละเคสอยู่ในไฟล์ config
php artisan prompt:eval --filter=pixel_premade

# เก็บผลเป็นไฟล์ JSON ไว้ดูย้อนหลัง/ส่งต่อ
php artisan prompt:eval --json=/tmp/eval.json
```

จะได้ผลแบบนี้ต่อเคส:

```
✅ [pixel_premade] ขอบัญชีที่สร้างพิกเซลมาแล้ว (conv #1539, 21 ส.ค.) (3/3 รอบผ่าน)
❌ [bm_with_unit] BM+หน่วยนับ = สั่งซื้อ ห้ามถามซ้ำ (regression คู่กับ 6) (2/3 รอบผ่าน)
   - ต้องมี "5,500" แต่ไม่พบ
   คำตอบ: BM มีกี่ตัวก็ได้ครับ...
```

แล้วปิดท้ายด้วยสรุปรวม (ผ่านกี่/ทั้งหมดกี่เคส, เวลารวม, ค่าใช้จ่ายรวมโดยประมาณ)

**เคสไหนถือว่า "ผ่าน" ต้องผ่านครบทุกรอบที่สั่งด้วย `--runs`** — ถ้ารัน `--runs=3` แล้วผ่าน 2/3 ถือว่า
เคสนั้นตก

## วิธีรันบน prod

```bash
railway ssh -- php /var/www/html/artisan prompt:eval
```

**หมายเหตุ:** container บน prod รากอยู่ที่ `/var/www/html` ไม่ใช่ `/app` — ต้องระบุ path เต็มแบบนี้

## ทำไมต้องรันหลายรอบ (`--runs`)

บอทตอนนี้ตั้ง temperature ไว้ที่ 0.40 คำตอบจึงไม่ได้เหมือนเดิม 100% ทุกครั้งที่ถามคำถามเดียวกัน —
รันรอบเดียวอาจ "บังเอิญผ่าน" หรือ "บังเอิญตก" ก็ได้ ก่อนขึ้น prod จริงแนะนำสั่ง `--runs=3` ขึ้นไป
เพื่อลดโอกาสหลอกตัวเอง

## วิธีเพิ่มเคสใหม่

**กฎ: ทุกครั้งที่แก้ prompt เพราะมีเคสจริงบน prod มาพัง ต้องเพิ่มเคสนั้นเข้าไฟล์ชุดทดสอบด้วยเสมอ**
ไม่งั้นครั้งหน้าที่แก้ prompt เรื่องอื่น อาจทำเคสเดิมพังซ้ำแบบไม่มีใครรู้

1. เปิด `config/prompt-eval-cases.php`
2. เพิ่ม element ใหม่ในอาร์เรย์ พร้อมคอมเมนต์บอกที่มา (เลขบทสนทนา/วันที่/PR) ไว้เหนือเคส
3. รันเฉพาะเคสนั้นยืนยันก่อน commit: `php artisan prompt:eval --filter=<id ที่ตั้งไว้>`

ตัวอย่างเคส:

```php
// ลูกค้าถามราคาแบบสั้น ๆ ห้ามโดน guardrail กันคำถามที่ไม่เกี่ยวสินค้าบล็อก (conv #1600, 21 ส.ค.)
[
    'id' => 'price_short_question',
    'label' => 'ลูกค้าถามราคาแบบสั้น ๆ ห้ามโดน guardrail บล็อก (conv #1600, 21 ส.ค.)',
    'message' => 'ราคา?',
    'expect_off_topic' => false,
    'must_contain' => [
        ['1,100'],
    ],
    'must_not_contain' => ['ไม่เข้าใจคำถาม'],
],
```

field ที่ใช้ได้ในแต่ละเคส (ทุก field เป็น optional ยกเว้น `id`/`label`/`message`):

| field | ใช้ทำอะไร |
|---|---|
| `id` | ตัวระบุไม่ซ้ำกัน ใช้กับ `--filter` |
| `label` | คำอธิบายเคสภาษาไทย |
| `history` | บทสนทนาก่อนหน้า (มี = จำลองว่าลูกค้าคุยมาแล้วหลายรอบ, ไม่มี = เริ่มทักครั้งแรก) |
| `message` | ข้อความล่าสุดจากลูกค้าที่จะยิงเข้าไป |
| `must_contain` | คำตอบต้องมีคำเหล่านี้ (ดูกติกา OR/AND ด้านล่าง) |
| `must_not_contain` | คำตอบห้ามมีคำเหล่านี้เลยแม้แต่คำเดียว |
| `expect_off_topic` | ต้อง (true) หรือห้าม (false) โดน guardrail กันคำถามนอกเรื่องบล็อก |
| `expect_order` | ยอด/รายละเอียดออเดอร์ที่ต้องตรง เมื่อคำตอบต้องมีการสรุปออเดอร์ |

กติกาของ `must_contain`: แต่ละแถวย่อย (`[...]`) คือกลุ่ม "หรือ" — เจอคำใดคำหนึ่งในกลุ่มก็ถือว่ากลุ่ม
นั้นผ่าน แต่ **ทุกกลุ่มต้องผ่านหมด** คำตอบถึงจะผ่านเคส เช่นตัวอย่างเคส `pixel_premade` ต้องมีทั้งคำว่า
"ไม่มี" และคำในกลุ่ม "สร้างพิกเซลเองได้/สร้างเองได้/สร้างพิกเซลเอง" (มีคำใดคำหนึ่งในกลุ่มก็พอ)

## ข้อจำกัดที่ต้องรู้

- **มีค่าใช้จ่ายเล็กน้อยทุกครั้งที่รัน** เพราะแต่ละเคสยิงไปหา AI จริง 1 ครั้ง (ยิ่งตั้ง `--runs` สูง
  ยิ่งยิงหลายครั้ง) และแต่ละเคสใช้เวลาประมาณ 5-10 วินาที รันทั้งชุด 20 เคสจึงไม่ใช่ของฟรีหรือของเร็ว
  ไม่ควรรันพร่ำเพรื่อโดยไม่มีเหตุผล
- **ชุดนี้กันได้แค่ "เคสเก่าพังซ้ำ"** ไม่ได้การันตีว่าบอทจะตอบถูกในสถานการณ์ใหม่ที่ยังไม่เคยเจอ —
  เจอเคสแปลกใหม่พังบน prod เมื่อไหร่ ให้ทำตามหัวข้อ "วิธีเพิ่มเคสใหม่" ด้านบนเพื่อปิดช่องโหว่ถาวร
- ถ้าเคสตกตั้งแต่รอบแรกหลังเพิ่มเคสใหม่ ให้พิจารณาก่อนว่าเกณฑ์ที่ตั้งไว้เข้มเกินไปหรือเปล่า (เช่น
  บังคับคำเป๊ะเกินไป) แล้วปรับที่ **เกณฑ์ในเคส** — อย่าไปแก้ prompt ตามเกณฑ์ที่ตั้งผิด

## ภาคผนวกทางเทคนิค (สำหรับ dev)

- คำสั่งอยู่ที่ `app/Console/Commands/PromptEval.php` (signature: `prompt:eval {--bot=26}
  {--runs=1} {--filter=} {--json=}`), ตัวรันจริงอยู่ที่
  `app/Services/PromptEval/PromptEvalRunner.php`
- ทดสอบผ่าน `tests/Unit/PromptEvalRunnerTest.php` (assertion engine) และ
  `tests/Feature/Console/PromptEvalCommandTest.php` (command wiring)
- เคสที่ไม่มี `history` เดินทางผ่าน `AIService::generateResponse()`, เคสที่มี `history` เดินทางผ่าน
  `RAGService::generateResponse()` (ใช้ flow เริ่มต้นของบอทที่ระบุด้วย `--bot`) — ทั้งสองเรียกด้วย
  `conversation: null` เสมอ จึงไม่มีอะไรเขียนลง DB
- needle ใน `must_contain`/`must_not_contain` ที่ขึ้นต้นและลงท้ายด้วย `/` จะถูกตีความเป็น regex
  (เช่น `/1,?100/`) นอกนั้นเทียบแบบ substring แบบไม่สนตัวพิมพ์เล็ก-ใหญ่
  ก่อนเทียบ runner จะ normalize คำตอบ: ตัดตัวคั่นข้อความ (bubble separator) `|||` ออก แล้วยุบ
  whitespace ต่อเนื่องให้เหลือช่องว่างเดียว
- `expect_order` เทียบกับ `order_payload` ที่ตัดออกมาจากบล็อก `[[ORDER]]...[[/ORDER]]` ใน
  คำตอบดิบ (ใช้ `!=` แบบ loose comparison ต่อ key)
- exit code: `0` เมื่อทุกเคสผ่านครบตาม `--runs`, `1` เมื่อมีอย่างน้อย 1 เคสตก — ใช้เช็คใน script/CI ได้
