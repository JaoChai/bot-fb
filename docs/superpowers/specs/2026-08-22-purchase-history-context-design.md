# Spec: ให้บอทรู้ประวัติการซื้อล่าสุดของลูกค้า

วันที่: 2026-08-22 · สถานะ: อนุมัติแล้ว รอเขียนแผน implement

## ปัญหา

ลูกค้า conv #1530 ซื้อ Nolimit Personal 3 ตัว (3,300 บาท) เมื่อ 15 ส.ค. กลับมาถามต่อเนื่องเรื่อง
บัญชีที่ถืออยู่เมื่อ 21 ส.ค. บอทตอบว่า "สวัสดีครับพี่ สนใจตัวไหนดีครับ?" แล้วเสนอเฟสไก่ 50 บาทให้

สาเหตุ: `ConversationContextService::autoClearIfIdle()` ล้าง context เมื่อเงียบเกิน 6 ชม.
(819 จาก 949 บทสนทนาของบอท 26 เคยถูกล้าง) บอทจึงอ่านเฉพาะข้อความหลังเส้นที่ล้าง

ตาข่ายที่ควรรับไว้มี 2 ชั้น และไม่ทำงานทั้งคู่สำหรับลูกค้ารายนี้:

1. **VIP note** — ต้องซื้อครบ 3 ออเดอร์ใน 12 เดือน (`rag.vip.threshold`) ลูกค้ารายนี้ซื้อครั้งเดียว
2. **ความจำอัตโนมัติ** (`ExtractEntitiesJob` → `auto_entity_extraction`) — **ตายมาตั้งแต่ 18 มี.ค. 2026**
   เพราะ job สั่งตัวเองเข้าคิว `low` (`ExtractEntitiesJob:42`) แต่ worker ทั้ง 3 ตัวฟังแค่
   `llm,webhooks,default` (ตรวจ Dockerfile ครบ 19 เวอร์ชัน ไม่เคยมีตัวไหนฟัง `low`)
   ยืนยันบน prod: คิว `low` มีงานค้าง 460 งาน เก่าสุด 15 พ.ค. ใหม่สุดวันนี้ · โน้ตทั้ง 298 อัน
   ในระบบเป็น VIP note ทั้งหมด ไม่มีอันไหนมาจาก entity extraction

**ขอบเขต spec นี้: แก้เฉพาะข้อ "บอทต้องจำได้ว่าลูกค้าเคยซื้ออะไร"**
เรื่องคิว `low` ที่ตายเป็นงานแยก ไม่อยู่ใน spec นี้ (ดูหัวข้อ "นอกขอบเขต")

## สิ่งที่ต้องได้

บอทรู้ว่าลูกค้ารายนี้เคยซื้ออะไรไปเมื่อไหร่ **โดยไม่พูดถึงมันก่อน** และไม่ให้ประวัติไปขัดกับกฎสต็อก

| ข้อกำหนด | ค่าที่ตกลง |
|---|---|
| ข้อมูลที่จำ | สินค้า + จำนวน + วันที่ ของออเดอร์ล่าสุด **1 ใบ** |
| ย้อนหลังได้ | **90 วัน** |
| การเอ่ยถึง | รู้ไว้เงียบๆ **ห้ามเอ่ยก่อนลูกค้าพูดถึง** ห้ามใช้ทักทาย |
| ลำดับกับสต็อก | **สต็อกชนะเสมอ** — ของที่เคยซื้อหมด ต้องเสนอตัวแทนตามกฎเดิม |

## วิธีทำ

### จุดที่แก้

`app/Services/RAGService.php` ไฟล์เดียว — ทุกเส้นทาง (มี/ไม่มี history, LINE/Telegram/Facebook)
วิ่งผ่าน `RAGService::generateResponse()` หมด (`AIService.php:69` เรียกต่ออีกที)

### ข้อมูลที่ดึง

ออเดอร์ `status = 'completed'` ล่าสุด 1 ใบของ `customer_profile_id` นั้น ที่ `created_at` อยู่ใน
90 วัน พร้อม `order_items` ของใบนั้น (`product_name`, `variant`, `quantity`)

- ใช้เกณฑ์ `status = 'completed'` แบบเดียวกับ `VipDetectionService::getTopItems()` เพื่อความสอดคล้อง
  (ตรวจ prod แล้ว: ออเดอร์ทั้ง 1,795 ใบเป็น `completed` ทั้งหมด เป็นสถานะเดียวที่ระบบใช้จริง)
- ใช้ index ที่มีอยู่ `orders_customer_profile_id_created_at_index`
- ไม่ต้องเพิ่ม index ให้ `order_items` (มีแค่ 2,075 แถว และดึงออเดอร์ใบเดียว)
- เรียงด้วย `created_at DESC, id DESC` แล้ว `limit 1` — ผูก tiebreaker ไว้กันกรณีลูกค้ามีหลายออเดอร์
  ใน timestamp เดียวกัน (เคยเกิดจริง: ลูกค้าซื้อเพิ่มในบทสนทนาเดียว)
- รูปแบบวันที่ในบล็อก: `d M Y` แบบไทยย่อ (เช่น `15 ส.ค. 2026`) ต่างจาก VIP note ที่ใช้ `Y-m-d`
  เพราะบล็อกนี้ให้ LLM อ่านเป็นภาษาไทยล้วน

### บล็อกที่ฉีดเข้า prompt

วางใน `buildEnhancedPrompt()` **ตำแหน่งเดียวกับบล็อก Memory เดิม คือก่อน stock injection**
เหตุผล: stock reminder ถูกวางไว้ท้ายสุดของ prompt อยู่แล้ว (ใกล้ข้อความลูกค้าที่สุด = LLM ให้
น้ำหนักสูงสุด) ประวัติที่อยู่ต้นๆ จึงถูกกฎสต็อกทับโดยธรรมชาติของตำแหน่ง

```
## ประวัติการซื้อล่าสุดของลูกค้ารายนี้ (ข้อมูลจากระบบออเดอร์จริง)
- Nolimit Level Up+ Personal (ผูกบัตร) x3 — 15 ส.ค. 2026

วิธีใช้: ใช้เพื่อเข้าใจบริบทคำถามที่ต่อเนื่องจากของที่ลูกค้าถืออยู่เท่านั้น
⛔ ห้ามเอ่ยถึงประวัตินี้ก่อนที่ลูกค้าจะพูดถึงเอง ห้ามทักทายด้วยประวัติ
⛔ ตัวเลขจำนวนนี้เป็นของออเดอร์เก่า ห้ามนำไปรวมกับออเดอร์ใหม่
⛔ ถ้าสินค้าที่เคยซื้อหมดสต็อก ให้ทำตามกฎสต็อกและเสนอตัวแทน ห้ามยึดประวัติ
```

### ความสัมพันธ์กับระบบเดิม

- **ไม่แตะ `memory_notes`** และไม่แตะ `VipDetectionService` เลย — VIP ที่ทำงานดีอยู่แล้วคงเดิมทุกอย่าง
- ลูกค้าที่เป็น VIP อยู่แล้วจะได้ทั้งสองบล็อก: บล็อก VIP เดิม (ยอดสะสม/สินค้ายอดนิยม) และบล็อกใหม่
  (ครั้งล่าสุดซื้ออะไร) ซึ่งของเดิมไม่มี
- เลือกออเดอร์ใบเดียวเพื่อกัน prompt ยาวตามจำนวนออเดอร์ (มีลูกค้าที่มี 111 ออเดอร์ในระบบ)

### semantic cache

`RagCache::forBot()` แชร์ cache ทั้งบอท ไม่แยกตามลูกค้า ถ้าไม่ทำอะไรเลย คำตอบที่ปรุงจากประวัติของ
ลูกค้า A อาจถูกเสิร์ฟให้ลูกค้า B

**ต้องเพิ่มเงื่อนไขใน `RAGService::shouldSkipCache()`: มีประวัติการซื้อ → ข้าม cache**
(กฎเดียวกับที่ระบบใช้กับ `memory_notes` ของ VIP อยู่แล้ว)

⚠️ `shouldSkipCache()` ถูกเรียก **ก่อน** `buildEnhancedPrompt()` ในลำดับการทำงาน ถ้า implement ตรงๆ
จะ query ออเดอร์ 2 ครั้งต่อการตอบ 1 ครั้ง — ต้องดึงครั้งเดียวแล้วส่งผลต่อให้ทั้งสองจุดใช้ร่วมกัน
(เก็บใน property ของ request นั้น หรือส่งเป็น argument) **ห้าม query ซ้ำ**

ผลกระทบต่อค่าใช้จ่ายน้อยมาก — `rag_cache` ทั้งระบบมี 3 แถว hit_count เป็น 0 เพราะเงื่อนไขข้าม cache
เดิมกินเกือบทุกกรณีอยู่แล้ว (มี history / ข้อความสั้นกว่า 20 ตัวอักษร / พูดถึงชื่อสินค้า)

## Error handling

| กรณี | พฤติกรรม |
|---|---|
| `customer_profile_id` เป็น null | ข้าม ไม่ฉีดบล็อก |
| ไม่มีออเดอร์ใน 90 วัน | ข้าม ไม่ฉีดบล็อก (prompt เหมือนเดิมทุกตัวอักษร) |
| ออเดอร์มีแต่ `order_items` ว่าง | ข้าม |
| query throw exception | จับไว้ · `Log::warning` · คืนค่าว่าง · **บอทตอบลูกค้าต่อได้ตามปกติ** |

หลักการ: ความจำเป็นของเสริม ห้ามทำให้บอทตอบลูกค้าไม่ได้

## การทดสอบ

1. **Unit test** — ดึงถูกใบ (ล่าสุด/ใน 90 วัน/completed), คืนค่าว่างเมื่อไม่มีออเดอร์, คืนค่าว่างเมื่อ
   ไม่มี customer profile, ไม่ throw เมื่อ query ล้ม
2. **เคสใน `config/prompt-eval-cases.php`** — ลูกค้าเก่าถามต่อเนื่องแบบ conv #1530:
   บอทต้องไม่ทักเหมือนลูกค้าใหม่ ต้องไม่เสนอ G3D ให้คนที่ถือ Nolimit และ**ต้องไม่เอ่ยประวัติขึ้นมาเอง**
3. **เคสสต็อกหมด** — ลูกค้าเคยซื้อ BM + BM หมดสต็อก → บอทต้องเสนอ Personal ตามกฎ SUBSTITUTION เดิม
   ห้ามยึดประวัติแล้วขาย BM ต่อ

## นอกขอบเขต spec นี้

- **คิว `low` ที่ไม่มี worker** (460 งานค้าง ฟีเจอร์ entity extraction ตายมา 5 เดือน) — เป็นบั๊กคนละตัว
  ถ้าจะแก้ต้องล้างคิวเก่าก่อนเปิด worker ไม่งั้นจะยิง LLM 460 ครั้งรวดด้วยข้อมูลเก่า 3 เดือน
- **เกณฑ์ VIP 3 ออเดอร์** — ไม่แตะ เพราะป้าย VIP มีสิทธิพิเศษอื่นพ่วง (ข้ามแจ้งเตือน Support, fast track)
- **เวลา 6 ชม. ของ auto-clear** — ไม่แตะ กลไกนี้กันตะกร้าเก่าปนออเดอร์ใหม่ซึ่งเคยเป็นบั๊กจริงมาแล้ว
